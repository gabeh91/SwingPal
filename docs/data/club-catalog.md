# Club catalog

The Add Club catalog loads manufacturer model names and published club options from Supabase Storage. The last valid download is cached on device, and a reviewed snapshot ships with the app for first launch and offline use. It is not a shop inventory, a fitting database, or a complete historical archive.

## Data and provenance

- `Tools/club_catalog_sources.json` is the reviewed seed: 650 models, 1,974 selectable clubs, 22 brands, and 604 manufacturer sources reviewed on 2026-09-28. Automatic updates can add models beyond this seed without an app release.
- Each family has `sourceIDs` pointing to HTTPS manufacturer pages with a `checkedAt` date. Those records are also retained in the generated resource.
- `SwingPal/Resources/club_catalog.json` is generated by the Swift importer. The app decodes its existing `brands` and `families` contract; provenance is additive metadata.
- Seed manufacturer pages are reviewed manually. The previous PING keyword scraper and category-wide invented ranges have been removed. The app only downloads the Supabase JSON; the scheduled server function accesses supported manufacturer feeds. Builds and the Swift compiler are offline.

The snapshot covers Titleist, TaylorMade, PING, Callaway, Cobra, Mizuno, Takomo, PXG, Wilson, Cleveland, Srixon, Tour Edge, Scotty Cameron, LAB Golf, Honma, Miura, Odyssey, Bettinardi, Evnroll, New Level, Haywood and XXIO. Current and recent models take priority. Coverage is deliberately uneven: it includes selected recent ranges and some earlier clubs still documented by manufacturers. It does not assert that every model from these brands is included. Custom entry remains available for older or missing equipment.

Examples of primary sources include [Titleist's specification tables](https://www.titleist.com/golf-clubs/specifications), [PING G440 irons](https://ping.com/en-us/golf-clubs/irons/g440-iron), [Mizuno JPX925 specifications](https://mizunogolf.com/uk/golf-clubs/jpx925-series/jpx925-hot-metals/club-specification/) and [L.A.B. Golf's putter collection](https://labgolf.com/collections/putters). Every included model is traceable in the source JSON.

## Interpretation

1. A family represents a specific head model/set, such as Blueprint S or JPX925 Hot Metal Pro. Generic umbrellas such as T-Series, Blueprint and JPX925 are not selectable models.
2. Options represent verified published heads across available handedness. Some feeds expose only a subset of a model’s historical options; previously verified options are retained when stock changes. Availability varies by region, handedness and configuration; the UI does not promise availability to buy.
3. Iron numbers use `4I` etc.; P/W and G markings may be normalized to PW and GW. Manufacturer-specific UW and loft-marked set wedges are retained. Titleist metals that publish lofts instead of club numbers use those loft labels rather than inferred numbered heads.
4. Drivers expose one Driver entry per model. Shaft, flex, handedness, driver loft, adjustable-hosel settings, iron loft bending, wedge grind/bounce, putter length and cosmetic finishes are outside this bag-identification pass. Wedges merge grinds into their supported lofts. Some distinct manufacturer retail editions retain their original model names; known finish/handedness duplicates are normalized by the adapters. A named putter has one Putter entry.
5. Carry defaults are SwingPal starting estimates, not manufacturer specifications or measured player data. The review screen labels them as estimates and allows editing in the user's units. Loft-marked clubs and UW use appropriate estimate ranges, and putters never request a full-swing carry.
6. Existing saved clubs keep their UUID, name, brand, model and carry. Ambiguous old families cannot be safely mapped to a specific head, so there is no automatic bag migration. Exact saved names still deduplicate; a legacy generic family may coexist with a newly selected specific model until the user removes or edits it.
7. If neither a valid cache nor the bundled asset can be loaded, custom entry remains usable. The app does not silently substitute the old fabricated catalog.

## Hosting and automatic maintenance

Public object: `https://zhmvngzfhzyyvyseeaxi.supabase.co/storage/v1/object/public/club-catalog/v1/catalog.json`. Downloads require no login. No app user has catalog write access.

`ClubCatalogStore` refreshes at launch and when Add clubs opens, at most once per 24 hours after success. Failed requests back off for five minutes and retain the last valid data. Schema version, size, brands, model IDs and saved-club identities are validated before caching. The cache is tied to its project URL. Background updates do not replace a model or draft while the golfer is selecting clubs; the next sheet uses the newest snapshot. Saved bags and carries are never rewritten by a catalog update.

The `refresh-club-catalog` Edge Function runs daily at **03:00 UTC** through Supabase Cron (`13:00 Melbourne standard time`, `14:00 daylight time`). The user selected automatic publication after validation; there is no review queue.

1. Acquire a five-minute database lease to prevent overlapping publishers.
2. Read private `club-catalog-admin/source.json` and the last published catalog. Merge the reviewed snapshot while preserving previously published models, club identities and source references. Existing codes and display labels win when a feed changes spelling; removing or correcting identities requires a reviewed migration.
3. Fetch nine official manufacturer feeds concurrently with bounded pagination, response size and execution time. L.A.B. uses its stock-putter tag/title grammar. Other adapters read explicit club, loft, set-composition and putter-model options, with brand-specific vendor checks and accessory/custom-SKU filtering. Only explicitly stated iron ranges are expanded. A failed brand retains its last valid data and receives a `retained` result; successful brands continue. If every feed fails, publication stops.
4. Normalize whitespace and sorting, derive brands, remove unused source references and validate the complete catalog. Reject unknown schemas, unsourced models, unsafe source URLs, empty ranges and duplicate identities. Do not guess numbered iron ranges or interpret accessories as clubs.
5. Save private candidate and previous revisions, then replace the public object in one upload. An individual source failure retains that brand’s data. Complete validation, all-source or archive failures leave the public object untouched. A failed final HTTP response can have an uncertain upload outcome; the public object and revision should be checked before retrying. Every candidate is validated before that upload.
6. Record per-brand feed results, status/counts in `public.club_catalog_runs` and release the lease. Expired worker runs are marked failed on the next attempt.

**Automatic discovery covers L.A.B., Cobra, Tour Edge, Miura, Honma, Takomo, Bettinardi, Evnroll and New Level.** PING, Mizuno, XXIO and the other brands use reviewed manufacturer specification tables or production listings in the seed. Their models are published and served, but daily discovery is not yet automated for them. Sites that block automated access need a separate supported adapter; the job does not claim to browse every manufacturer. Disappearing products/options are retained for existing golfers. Runtime reports distinguish successful updates from retained data.

Private sources, revisions and run logs are service-only. The function checks a dedicated random secret stored in Supabase Vault and Edge secrets; a public app key cannot invoke it. The scheduled SQL contains no plaintext secret. Revision history is retained for rollback; no automatic history deletion is configured.

## Deploying and operating

Requires an active linked Supabase project, an existing CLI login, Swift and Deno. Review pending migrations, then run:

```sh
supabase db push --dry-run
python3 Tools/deploy_club_catalog.py
```

The script validates source/tests, applies migrations, deploys the function, uploads the private seed, publishes an initial catalog, verifies public access, then enables the daily job. It reads credentials through the existing CLI session, never prints them, and deletes its temporary secret file. Re-running updates the source/function and the same named cron job. It does not create duplicate jobs. If initial publication fails, a new job is not enabled; an existing job retains its prior schedule.

Run the deployed importer immediately without redeploying:

```sh
python3 Tools/refresh_club_catalog.py
```

Fetch a local preview without writing to Supabase:

```sh
deno run --allow-net --allow-read --allow-write Tools/preview_club_catalog.ts /tmp/catalog-preview.json
```

The preview includes the seed plus all successful feeds, and writes a separate per-brand report. Review the result before promoting it to the seed and regenerating the offline bundle. The deployed function also merges the previous live revision, preserving history across runs.

Check actual worker results (the pg_cron SQL succeeds when an HTTP request is queued, before the worker finishes):

```sql
select started_at, finished_at, status, detail
from public.club_catalog_runs order by started_at desc limit 20;
select jobname, schedule, active from cron.job where jobname = 'refresh-club-catalog';
select status_code, timed_out, error_msg from net._http_response order by id desc limit 10;
```

To pause maintenance, use `select cron.alter_job(jobid, active := false) from cron.job where jobname = 'refresh-club-catalog';`. To trigger one run, use `select public.invoke_club_catalog_refresh();` and inspect the worker log after completion. To roll back, pause the job and restore a validated private `revisions/<run-id>-previous.json` to the live object using service credentials. CDN caching is five minutes and device refresh is daily, so changes are not immediate on every device. Correct the seed/adapter before resuming. Retired-model removal requires an explicit reviewed catalog operation; routine maintenance never deletes models.

To add another brand adapter, use official structured product/specification data, pin the accepted field grammar and hosts, add fixtures for real variants and feed failures, and call it before publication. Each adapter must independently validate before its output is merged. A failing adapter cannot replace its brand’s data; at least one adapter must succeed for a publication.

## Updating

Open the manufacturer's specification table or product collection and verify both the specific model and every selectable option. Add or update the explicit family record and its source date. Use separate model names when different generations have different ranges; do not infer a range from a similarly named model. Do not import marketing copy, imagery, prices, reviews or customer data.

From the repository root:

```sh
swift Tools/club_catalog_import.swift --source Tools/club_catalog_sources.json --output SwingPal/Resources/club_catalog.json
swift Tools/club_catalog_import.swift --source Tools/club_catalog_sources.json --output SwingPal/Resources/club_catalog.json --check
python3 -m unittest discover -s Tools/tests -p test_club_catalog_import.py
```

The compiler requires explicit nonempty variants and source references, validates source dates/URLs, rejects duplicate model and variant identities, and sorts output deterministically. Invalid input leaves the previous bundle untouched. `--check` detects missing/stale output without writing. The old `--seed-file` and `--emit-seeds` options are intentionally unsupported because name-only seeds cannot establish real club ranges.

Run the SwingPal XCTest suite after updating, including `ManufacturerCatalogTests` and `RemoteClubCatalogTests`, then inspect Add Club in a simulator. Run `deno test supabase/functions/refresh-club-catalog` and `deno check supabase/functions/refresh-club-catalog/index.ts` for server changes. The bundled integration checks exercise real-model search, published ranges and named-putter selection; importer tests cover invalid input and reproducibility. Deploy the updated private seed with the deployment script when ready.
